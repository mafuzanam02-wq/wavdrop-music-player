# WDBK-1 Benchmark Evidence

Evidence required by [ADR-001](adr/ADR-001-wdbk-backup-container.md) section 6.2. Generated by
`WdbkBenchmarkReportTest` (JVM unit test, synthetic fixtures; report written to `app/build/reports/wdbk-benchmark.txt`).
**Environment-specific:** desktop JVM (OpenJDK 21, 512 MiB test heap), not an Android device, and measured while other
Gradle work was running, so wall-clock numbers are noisy. The test asserts no time or ratio; it only asserts that every
fixture round-trips with an identical semantic fingerprint.

## Size and time (chunk size 2 000)

| fixture | songs | events | legacy JSON KiB | WDBK KiB | WDBK / JSON |
|---|---:|---:|---:|---:|---:|
| small | 60 | 300 | 201 | 21 | 0.104 |
| medium | 2 000 | 20 000 | 9 763 | 1 220 | 0.125 |
| large (event-heavy) | 4 000 | 100 000 | 42 894 | 5 774 | 0.135 |

Legacy JSON is pretty-printed (as shipped); WDBK is compact JSON + DEFLATE. No ratio is promised to users.

Export / decode wall-clock on the large fixture (one noisy run each, desktop JVM; the in-memory snapshot adapter, not the
production database source): legacy export about 3.9 s, WDBK export about 4.3 s (includes SHA-256 per entry, DEFLATE and the
canonical event sort), legacy parse about 2.2 s, WDBK decode + full verification about 1.5 s. Treat WDBK export as somewhat
slower than legacy and decode as comparable; do not read more into them.

## Chunk size choice: 2 000 events

Sweep on the 100 000-event fixture:

| events/chunk | chunks | WDBK KiB | largest history entry KiB |
|---:|---:|---:|---:|
| 250 | 400 | 6 038 | 75 |
| 500 | 200 | 5 894 | 149 |
| 1 000 | 100 | 5 813 | 298 |
| **2 000** | **50** | **5 774** | **597** |
| 5 000 | 20 | 5 751 | 1 491 |
| 10 000 | 10 | 5 743 | 2 982 |
| 25 000 | 4 | 5 738 | 7 455 |

Compression keeps improving only marginally above ~2 000 events (2 000 is within 0.6 % of 10 000), while the largest
transient JSON array/String per chunk grows linearly (0.6 MB at 2 000, 3 MB at 10 000). Smaller chunks lose size
(250 is +4.6 %) and add per-entry overhead (400 entries). 2 000 balances the two and keeps even multi-million-event
histories far under the 4 096-entry limit. Time differences in the sweep were within run-to-run noise.

## Export architecture (corrected) and memory

WDBK export is a true stream: `WdbkWriter` pulls the history from a `WdbkEventSource` one 2 000-event chunk at a time,
encodes one bounded JSON array, writes/hashes it, feeds the same events into the incremental semantic fingerprint, counts
them and drops the chunk. The production source (`CanonicalEventStream`) pages the database by a full-order keyset
(`occurredAt, songId, eventType, listenedMs, durationMs, source, COALESCE(eventId,''), id DESC`; the descending id reproduces
the legacy `getAllSnapshot()` tie order) up to a boundary captured once;
rows arrive already in the fingerprint's canonical order, so there is no app-side sort and no timestamp-run buffer. **No complete `List<BackupListenEvent>` exists on the WDBK export path.** (An earlier
candidate paged the database but still collected every event before writing, and a second candidate still buffered one
whole equal-`occurredAt` run; both have been removed. A 55 000-event history sharing a single `occurredAt` is a unit test.)

### True streamed export (events generated lazily; output discarded)

| events | WDBK KiB | chunks | largest history chunk KiB (uncompressed) | export ms | sampled heap peak MiB* |
|---:|---:|---:|---:|---:|---:|
| 100 000 | 2 782 | 50 | 551 | 2 299 | 303.3 |
| 500 000 | 12 876 | 250 | 553 | 15 717 | 315.3 |

(Sizes differ from the table above because this synthetic stream has strictly increasing timestamps/ids and is more
compressible; use it only for the memory shape.) The key observation is that **five times more history did not raise the
sampled heap** (303.3 vs 315.3 MiB) and the largest encoded chunk stays about 0.55 MB. The in-memory
adapter path grew with history on the earlier table (274 MiB at 20 000 events, 508 MiB at 100 000), but that comparison
is indicative only (see caveats).

### Caveats (stated, not hidden)

- A reliable per-operation peak cannot be measured from a JVM unit test, and Android device memory was NOT measured. The
  sampled heap mark (2 ms sampler) includes uncollected garbage and whatever earlier fixtures left behind in the same JVM
  (hence the ~300 MiB floor); it is a coarse indicator, not live memory. No absolute heap improvement is promised.
- Deterministic proxy: the largest single contiguous text payload on export is one chunk (about 0.55-1.1 MB) versus the
  entire document for legacy v2 JSON (42 894 KiB for the 100 000-event fixture).
- The history export retains one database page, one WDBK chunk, a fixed cursor and the previous event (bounded by the
  configured 2 000-row page/chunk sizes, independent of history size and of how many events share a timestamp), plus the
  small sections and the song map. SQLite sorts each page inside the query and may use its own temp storage; the query
  seeks the `occurredAt` index and then needs `USE TEMP B-TREE FOR RIGHT PART OF ORDER BY` for the remaining keys (the plan
  is pinned by a test; a mixed-direction OR predicate was rejected because it changed the plan to a MULTI-INDEX OR with a
  full sort per page). A very large single-timestamp group is re-scanned and re-sorted per page by SQLite (CPU/temp
  storage, not app memory).
- One theoretical failure mode: if SQLite's code-point text order and the fingerprint's UTF-16 string order disagree for
  two rows tied on every earlier key (eventIds differing at a supplementary character versus U+E000..U+FFFF), the export
  stops with a clear error instead of writing a wrong fingerprint. App-generated eventIds are UUIDs; it has a test.
- **Import / restore is unchanged**: the decoder reconstructs the complete `WavdropBackup` because Merge and Recovery use
  that model, so the decoded event list is fully materialized (and verification after export briefly holds that decoded
  model). Going further there needs a streaming restore model (WDBK-2-era work), not part of WDBK-1.
